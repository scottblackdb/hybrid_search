Read this before changing the repo. Human-facing goals live in [README.md](README.md). This file is the working memory for later agents.

## Mission

Build a Databricks demo: synthetic clinical data lands in Unity Catalog Delta, embedding **source text** is prepared, vectors are generated later, a **subset** is served in Lakebase Postgres, and the app does **keyword + semantic (hybrid)** search.

Do not treat this as a production EHR. All data is synthetic. Catalog name `crisp` is a Maryland HIE-style demo brand, not a connection to real CRISP.

## Data model (after notebook run)

Grain and FKs:

```text
patients (patient_id)
  └── encounters (encounter_id, patient_id)
        ├── diagnoses (diagnosis_id, encounter_id, patient_id)
        ├── clinical_notes (note_id, encounter_id, patient_id)  # one per encounter
        └── orders (order_id, encounter_id, patient_id)
              └── order_details (order_detail_id, order_id, encounter_id, patient_id)
```

Default volumes (widgets can shrink for smoke tests):

| Table | Default rows | Notes |
|---|---:|---|
| `crisp.bronze.patients` | 2,000,000 | Includes `last_visited`, `next_scheduled_visit` |
| `crisp.bronze.encounters` | 8,000,000 | 80% of rows map to 20% high-utilizer patients |

`patient_idx` is written on `patients` and `encounters` as a generator helper; it is not required for search serving.

### `patients` columns

`patient_id`, `first_name`, `last_name`, `full_name`, `date_of_birth`, `sex`, `zip_code`, `city`, `state`, `insurance_plan`, `primary_facility`, `last_visited`, `next_scheduled_visit`, `is_high_utilizer`, `patient_idx`

- `last_visited`: DATE in last 5 years; **50% in last 3 years**, 50% in years 3–5.
- `AS_OF` in the notebook is **2026-10-21**. Keep date logic consistent with that unless the user changes it.
- Maryland geography (zips/cities) and Maryland-area facilities.

### `encounters` columns

`encounter_id`, `patient_id`, `encounter_date`, `encounter_facility`, `encounter_type`, `chief_complaint`, `discharge_disposition`, `embedding`, `encounter_idx`, `patient_idx`, `embedding_vector`

`embedding` = `chief_complaint`

### `orders` columns

`order_id`, `encounter_id`, `patient_id`, `order_datetime`, `ordering_provider`, `order_type`, `order_status`, `ordering_facility`

No embedding column. `ordering_provider` is picked from a 200-name list (80 hand-seeded names, then filled from `FIRST_NAMES`/`LAST_NAMES`).

### `order_details` columns

`order_detail_id`, `order_id`, `patient_id`, `encounter_id`, `loinc_code`, `test_name`, `specimen_type`, `sample_id`, `collected_at`, `resulted_at`, `result_value`, `result_unit`, `result_flag`, `result_comment`, `embedding`, `embedding_vector`

`embedding` = `concat_ws(". ", test_name, result_comment)`

Lab catalog: 75 tests (`N_LAB_TESTS == 75`). Common metabolic/cardiac tests are over-weighted; remaining ~32% sample the full catalog.

### `diagnoses` columns

`diagnosis_id`, `encounter_id`, `patient_id`, `diagnosis_date`, `icd10_code`, `diagnosis_description`, `diagnosis_type`, `dx_family`, `clinical_note`, `embedding`, `embedding_vector`

`embedding` = `concat_ws(". ", diagnosis_description, clinical_note)`

### `clinical_notes` columns

`note_id`, `encounter_id`, `patient_id`, `note_datetime`, `note_type`, `author`, `author_role`, `note_facility`, `note_text`, `embedding`, `embedding_vector`

`embedding` = `note_text`. `note_id` = `NOTE-` + `encounter_idx`. Note sections: header, chief complaint, HPI (age/sex/setting, onset, high-utilizer history), vitals, exam, medical decision making (differential + workup by chief complaint), assessment (each encounter diagnosis with the reason it was assigned, from `DX_REASONING`), plan (per-diagnosis plan, Frederick courier-disruption clause in the outage window, disposition, follow-up), signature. All variation is hash-based on `encounter_idx` (no `rand`), so notes are reproducible. Diagnoses are assigned to encounters independently of chief complaint, so a note can pair unrelated complaint and diagnoses.

## Demo story (keep it in the data)

Frederick Health Hospital, **2026-03-01 through 2026-03-21**: lab courier disruption.

- Orders at that facility in the window have longer TAT, more `Pending`, and `result_comment` text containing **courier disruption**.
- Diagnoses with ICD `E11*` at Frederick mention delayed A1c/glucose.
- Clinical notes for Frederick encounters in the window state that HbA1c/BMP results may be delayed 3-14 days by the courier disruption.
- High utilizers are older, drive ~80% of child-table rows, and have inflated A1c/glucose/creatinine/BNP-style results.
- Use this for outreach queries: delayed labs + upcoming `next_scheduled_visit`.

Do not flatten distributions or remove this incident without an explicit user request.

## Lakebase search table (`02_load_lakebase_search`)

`search.search_documents` on `crisp-search`: one row per source row that has an `embedding_vector`, from encounters, order_details, diagnoses, and clinical_notes, **only for patients with `last_visited` within `last_visited_days` (default 365) of `AS_OF`** (~6.7M rows, ~335k patients at default scale).

- Columns: `doc_id` (PK = source id), `source_table`, patient filters (`full_name`, `date_of_birth`, `sex`, `zip_code`, `insurance_plan`, `primary_facility`, `last_visited`, `next_scheduled_visit`, `is_high_utilizer`), `event_at`, `facility`, `doc_type`, `title`, `author`, `icd10_code`, `dx_family`, `loinc_code`, `result_flag`, `order_status`, `content` (= `embedding` text), `embedding vector(1024)`, generated `content_tsv`.
- App-owned regular table (not a synced table), so indexes are allowed: B-tree filters, GIN on `content_tsv`, GIN trigram on `full_name`, HNSW `vector_cosine_ops` on `embedding`.
- Full reload each run (DROP + CREATE + JDBC append with `stringtype=unspecified` so `'[..]'` text casts to `vector`). One OAuth token is used for the load (1 h validity).
- **Build logic lives only in `search_documents.py`** and is a DataFrame built on the fly (no intermediate Delta table). `build_search_documents(spark, source, cutoff, changes=None)`: full load passes nothing (all four source tables); CDC passes `{source_table: CDF DataFrame}` (drop `update_preimage` first) and gets the same columns plus `_change_type`, `_commit_version`, `_commit_timestamp` for upsert/delete by `doc_id`. Lookups (patients, orders, encounter facility) always read current tables. `POSTGRES_COLUMNS` / `create_table_sql` define the Postgres schema; `to_postgres_rows` formats vectors. Do not duplicate this logic in notebooks.
- Not yet handled for CDC: changes to lookup tables (patient `last_visited` leaving the window, `next_scheduled_visit`, order status, encounter facility) need their own fan-out to affected `doc_id`s.
- Import the module with `databricks workspace import <dir>/search_documents.py --file notebooks/search_documents.py --format AUTO --overwrite --profile DEFAULT` so it lands as a FILE next to the notebook.
- Scale the `primary` compute up before loading / building HNSW; the default 1 CU is far too small for ~6.7M x 1024-dim.

## Search app (`crisp-hybrid-search/`)

Databricks App scaffolded with `databricks apps init --features lakebase,serving --package-manager npm` (AppKit 0.84.0, React 19 + Express, Vite). Profile `DEFAULT`. Bundle config is `databricks.yml` / `app.yaml`; resources: Lakebase `projects/crisp-search/branches/production` db `databricks-postgres` (`CAN_CONNECT_AND_CREATE`) and serving endpoint `databricks-gte-large-en` (`CAN_QUERY`). Local dev: `npm run dev` (port 8000, reads `.env`, which is gitignored by the scaffold; uses the DEFAULT profile).

```text
server/server.ts                  # createApp({ plugins: [lakebase(), server(), serving()] }) + setupSearchRoutes
server/routes/search-sql.ts       # buildSearchQuery(): the single hybrid SQL statement + steps + display params; DETAIL_SQL / RELATED_SQL
server/routes/search-routes.ts    # POST /api/search, GET /api/documents/:docId; embeds the query via WorkspaceClient.servingEndpoints.query
client/src/App.tsx                # state + layout; components/{Header,ResultsPane,DetailPane,SqlPane}.tsx; api.ts (types, fetch, formatters)
client/src/index.css              # all styling (plain CSS, no Tailwind classes)
grants.sql                        # GRANTs for the app service principal on search.search_documents
tuning.sql                        # statistics, VACUUM, partial notes HNSW index, optional pg_prewarm, EXPLAIN diagnostics
```

**Search behavior.** `POST /api/search` body `{ query, mode: hybrid|keyword|semantic, sources: [...], limit }`; every search is capped at `MAX_RESULTS` = 200 results (`search-sql.ts`; the client sends `RESULT_LIMIT` in `api.ts`, the server rejects larger limits, and each leg gathers `MAX_RESULTS` candidates). Hybrid embeds the query (`databricks-gte-large-en`, same model as the stored vectors), then one SQL statement runs a keyword leg and a semantic leg (200 candidates each (`MAX_RESULTS`), source filter applied inside each leg) and fuses them with reciprocal rank fusion (`1/(60+rank)` per leg). Keyword leg = `content_tsv @@ websearch_to_tsquery` OR exact `icd10_code`/`loinc_code`/`patient_id`/`doc_id` match OR trigram `full_name % q`. Semantic leg = `embedding <=> $2::vector` (HNSW). Keyword mode skips the embedding call and does not send `$2` (parameters are numbered dynamically). The route wraps the query in a transaction with `SET LOCAL hnsw.ef_search = 200` and `hnsw.iterative_scan = relaxed_order` so filtered vector scans return enough rows. The response returns the SQL text, display params (vector abbreviated), steps, session settings, and timings; the right pane renders these.

**Keyword-leg performance (measured by the user, cold cache).** Ranking every match of a common term was slow: `diabetes` matches ~750k of 6.7M rows, the planner correctly chose a parallel seq scan (GIN bitmap would random-read 750k rows), 462k blocks read from disk, ~4.1 s. So the keyword leg ranks at most `MATCH_CAP` matches (default 5,000, env `KEYWORD_MATCH_CAP`; 20,000 still took ~2 s because a dense term reads ~N/1.5 heap blocks at ~0.18 ms each, and seq scans use a ring buffer so reruns do not get cache hits) (`search-sql.ts`); rarer terms are still ranked exactly, very common terms are ranked over an arbitrary 20k subset. The exact-code and trigram-name conditions are only added for short queries (single token / 3 words or fewer) so long phrases get a plain full-text query. `grants.sql` sits beside `tuning.sql` (statistics, `VACUUM (ANALYZE)`, optional `pg_prewarm`, EXPLAIN diagnostics); `written=` in a plan means hint bits were being set because the table had not been vacuumed. The agent was not allowed to run queries against Lakebase, so all plan data comes from the user.

**Semantic-leg findings (user-run `EXPLAIN ANALYZE` plans; the agent cannot query Lakebase).**
- HNSW index `search_documents_embedding_hnsw_idx` exists and is used. Unfiltered ~1 s cold, fast warm (index scans use shared buffers, unlike big seq scans).
- With a source filter and a realistic query vector (seed from the same source) the filtered scan works: `diagnoses` 100 rows / ~465 ms cold, `encounters` 100 rows / ~425 ms cold, nothing discarded by the filter.
- `clinical_notes` (~13.5k rows, ~0.2%) took **18.6 s**: the planner skips the big HNSW index, bitmap-scans the notes and exact-sorts, detoasting each 4 KB vector (~9 block touches per row). Fixed by the partial index `search_documents_embedding_hnsw_notes_idx ... WHERE source_table = 'clinical_notes'` (created by the loader and `tuning.sql`): now 4.6 ms. The app's `source_table = ANY(...)` filter does match the partial index.
- Adversarial cross-source seeds (e.g. a diagnosis vector filtered to `encounters`) returned **0 rows** after scanning only a few thousand neighbours. Causes not confirmed: the default `hnsw.max_scan_tuples` (20000, now raised to 100000 in `SESSION_SETTINGS`) and possibly the iterative-scan memory limit (`hnsw.scan_mem_multiplier` x `work_mem`; one test also lacked the app's `work_mem`). Real queries are usually near several sources, so treat as an edge case. If a source chip returns few or no results in the app, add a partial HNSW index per source (or partition by `source_table`).
- Not yet tested: filtering to `order_details`, mixed filters such as notes + diagnoses, and the keyword leg at the 5,000 match cap.

**Compute/cache.** Seq scans use a ring buffer and do not populate `shared_buffers`, so reruns of keyword seq scans stay slow; index scans do cache. First queries after the compute restarts or scales to zero (default 5 min idle) are cold. Suggested but not applied: raise the `primary` endpoint's minimum size / disable scale-to-zero for demos; `pg_prewarm` of the index pages if the extension is allowed (commented in `tuning.sql`).

## Search architecture (intended, not all built)

**Keyword / BM25 / Postgres FTS / trigram:** names, ICD-10, LOINC, IDs, facilities, exact phrases.

**Semantic:** vectors from `embedding` text on encounters, order_details, diagnoses.

**Filters (do not embed):** dates, facilities, `result_flag`, `order_status`, `dx_family`, `patient_id`, insurance, `is_high_utilizer`.

**Hybrid:** filter first, retrieve keyword + vector candidates, fuse scores, return patient-joined hits.

Possible serving grains for Lakebase (vectors already exist on every row in the lakehouse):

1. Diagnosis documents (best clinical narrative).
2. Lab-result documents (delay / outreach story).
3. Encounter complaints (optional).

Do **not** default to syncing every `order_details` row (20M) to Lakebase. Prefer a subset: delayed Frederick labs, abnormal/critical flags, recent visits, or a sampled gold set plus the incident cohort.

## Coding conventions in this repo

- Databricks SOURCE notebooks: `# Databricks notebook source`, cells split by `# COMMAND ----------`, markdown via `# MAGIC %md`.
- Fully qualify `crisp.bronze.table`; do not rely on `USE CATALOG`.
- Deterministic hashes + `F.rand(integer_seed)` — **integer seeds only**, never a Column.
- A `F.rand`/`F.randn` draw referenced more than once (multiple `.when` branches, or reused across columns) must be materialized with `.withColumn("_x_r", F.rand(n))` and read via `F.col`. Inline reuse re-evaluates per reference and short-circuited `CASE` branches drift (verified on serverless: 50/25/25 became 50/37.5/12.5).
- Timestamps: use `F.timestamp_seconds(...)`, not `F.from_unixtime` (returns STRING).
- `pick_from` is 1-based `element_at` on a Python list via `F.lit(values)`.
- Overwrite Delta with `.option("overwriteSchema", "true")`.
- After write: CDF `delta.enableChangeDataFeed = true`, then `CLUSTER BY` patient-oriented keys.
