## Mission

Build a Databricks demo: synthetic clinical data lands in Unity Catalog Delta, embedding **source text** is prepared, vectors are generated later, a **subset** is served in Lakebase Postgres, and the app does **keyword + semantic (hybrid)** search.

Do not treat this as a production EHR. All data is synthetic. Catalog name `crisp` is a Maryland HIE-style demo brand, not a connection to real CRISP.

### `clinical_notes` columns

`note_id`, `encounter_id`, `patient_id`, `note_datetime`, `note_type`, `author`, `author_role`, `note_facility`, `note_text`, `embedding`, `embedding_vector`

All variation is hash-based on `encounter_idx` (no `rand`), so notes are reproducible. Diagnoses are assigned to encounters independently of chief complaint, so a note can pair unrelated complaint and diagnoses.

## Demo story (keep it in the data)

Frederick Health Hospital, **2026-03-01 through 2026-03-21**: lab courier disruption.

- Orders at that facility in the window have longer TAT, more `Pending`, and `result_comment` text containing **courier disruption**.
- Diagnoses with ICD `E11*` at Frederick mention delayed A1c/glucose.
- Clinical notes for Frederick encounters in the window state that HbA1c/BMP results may be delayed 3-14 days by the courier disruption.
- High utilizers are older, drive ~80% of child-table rows, and have inflated A1c/glucose/creatinine/BNP-style results.
- Use this for outreach queries: delayed labs + upcoming `next_scheduled_visit`.

Do not flatten distributions or remove this incident without an explicit user request.

## Lakebase search table (`02_load_lakebase_search`)

`search.search_documents` on `crisp-search`: one row per source row that has an `embedding_vector`, from encounters, order_details, diagnoses, and clinical_notes, **only for patients with `last_visited` within `last_visited_days` (default 365) of `AS_OF`** (~6.7M rows, ~335k patients at default scale).

- Columns: `doc_id` (PK = source id), `source_table`, patient filters (`full_name`, `date_of_birth`, `sex`, `zip_code`, `insurance_plan`, `primary_facility`, `last_visited`, `next_scheduled_visit`, `is_high_utilizer`), `event_at`, `facility`, `doc_type`, `title`, `author`, `icd10_code`, `dx_family`, `loinc_code`, `result_flag`, `order_status`, `content` (= `embedding` text), `embedding vector(1024)`, generated `content_tsv`.
- App-owned regular table (not a synced table), so indexes are allowed: B-tree filters, GIN on `content_tsv`, GIN trigram on `full_name`, HNSW `vector_cosine_ops` on `embedding`, plus a small partial HNSW index `search_documents_embedding_hnsw_notes_idx` `WHERE source_table = 'clinical_notes'` (notes are sparse; see Search app findings). The loader ends with `ALTER ... SET STATISTICS 1000` on `content_tsv`/`full_name`/`source_table`/`facility` and `VACUUM (ANALYZE)`.
- Full reload each run (DROP + CREATE + JDBC append with `stringtype=unspecified` so `'[..]'` text casts to `vector`). One OAuth token is used for the load (1 h validity).
- **Build logic lives only in `search_documents.py`** and is a DataFrame built on the fly (no intermediate Delta table). `build_search_documents(spark, source, cutoff, changes=None)`: full load passes nothing (all four source tables); CDC passes `{source_table: CDF DataFrame}` (drop `update_preimage` first) and gets the same columns plus `_change_type`, `_commit_version`, `_commit_timestamp` for upsert/delete by `doc_id`. Lookups (patients, orders, encounter facility) always read current tables. `POSTGRES_COLUMNS` / `create_table_sql` define the Postgres schema; `to_postgres_rows` formats vectors. Do not duplicate this logic in notebooks.
- Not yet handled for CDC: changes to lookup tables (patient `last_visited` leaving the window, `next_scheduled_visit`, order status, encounter facility) need their own fan-out to affected `doc_id`s.
- Import the module with `databricks workspace import <dir>/search_documents.py --file notebooks/search_documents.py --format AUTO --overwrite --profile DEFAULT` so it lands as a FILE next to the notebook.
- Scale the `primary` compute up before loading / building HNSW; the default 1 CU is far too small for ~6.7M x 1024-dim.

### How a search works

`POST /api/search` body `{ query, mode: hybrid|keyword|semantic, sources: [...], limit }`. Every search is capped at `MAX_RESULTS` = 200 (`search-sql.ts`); the client sends `RESULT_LIMIT` (`api.ts`), the server rejects larger limits, and each leg gathers `MAX_RESULTS` candidates (fewer would cap a hybrid page below 200).

- **Embedding:** hybrid and semantic embed the query with `databricks-gte-large-en` (same model as the stored vectors). Keyword mode skips it.
- **Parameters** are numbered dynamically: only parameters the chosen mode references are sent (query text is absent in semantic mode, the vector is absent in keyword mode); Postgres rejects unused parameters with "could not determine data type of parameter".
- **Keyword leg:** `content_tsv @@ websearch_to_tsquery('english', q)`, ranked by `ts_rank_cd`. The exact `icd10_code`/`loinc_code`/`patient_id`/`doc_id` match is added only for single-token queries; trigram `full_name % q` only for queries of up to 3 words and 40 chars. Score terms are `coalesce`d and sorted `NULLS LAST` (a NULL exact-match term once made every FTS-only row sort first). At most `MATCH_CAP` matches are ranked (default 5000, env `KEYWORD_MATCH_CAP`, must be >= `MAX_RESULTS`).
- **Semantic leg:** `embedding <=> $n::vector` (HNSW), with the source filter applied inside the leg.
- **Fusion (hybrid):** reciprocal rank fusion `1/(60+rank)` per leg, FULL JOIN on `doc_id`, then join back for display columns.
- **Transaction:** the route runs the query in a transaction with `SESSION_SETTINGS`: `work_mem = 64MB`, `hnsw.ef_search = 200`, `hnsw.iterative_scan = relaxed_order`, `hnsw.max_scan_tuples = 100000`.
- **Response:** results, SQL text, display params (vector abbreviated), steps, session settings, and timings `{embedMs, queryMs}`; the right pane renders these. The SELECT casts `rrf`/scores to `float8` and ranks to `int` (the `pg` driver returns `numeric`/`bigint` as strings).
- **Detail:** `GET /api/documents/:docId` returns the record, patient fields, and up to 15 other records for the patient.

### Measured performance (user-run `EXPLAIN ANALYZE`; the agent cannot query Lakebase)

- **Keyword, common term:** `diabetes` matches ~750k of 6.7M rows (~11%). The planner correctly seq-scans (a GIN bitmap would random-read 750k rows). Uncapped: 457-462k blocks read, 4 s to 39 s depending on storage latency. Capped at 20000: 13.3k blocks, ~2.1-2.4 s, because a dense term reads ~N/1.5 heap blocks at ~0.18 ms each. That is why the default cap is 5000 (expected ~0.5 s; not yet measured). Rarer terms (fewer matches than the cap) are ranked exactly; very common terms are ranked over the first matches found, not the best. Seq scans use a ring buffer and do not populate `shared_buffers`, so reruns do not get faster.
- **Semantic, unfiltered:** `search_documents_embedding_hnsw_idx` is used; ~1 s cold, fast warm (index pages do cache).
- **Semantic, source filter, realistic seed (same source):** `diagnoses` 100 rows / ~465 ms cold; `encounters` 100 rows / ~425 ms cold.
- **Semantic, `clinical_notes`:** 18.6 s before the partial index (planner exact-sorted ~13.5k notes, detoasting each 4 KB vector, ~9 block touches per row); 4.6 ms after `search_documents_embedding_hnsw_notes_idx`. The app's `source_table = ANY(...)` filter matches the partial index.
- **Open edge case:** an adversarial seed (a diagnosis vector filtered to `encounters`) returned 0 rows after scanning a few thousand neighbours. Cause unconfirmed: the default `hnsw.max_scan_tuples` (20000, now 100000 in the app) and/or the iterative-scan memory limit (`hnsw.scan_mem_multiplier` x `work_mem`; that test also lacked the app's `work_mem`). If a source chip returns few or no results in the app, add a partial HNSW index per source (or partition by `source_table`).
- **Not yet tested:** filtering to `order_details`; mixed filters such as notes + diagnoses; the keyword leg at the 5000 cap; the 200-candidate legs; end-to-end timings in the deployed app.
- **Compute/cache:** first queries after a restart or scale-to-zero (default 5 min idle) are cold. Suggested, not applied: raise the `primary` endpoint's minimum size / disable scale-to-zero for demos; `pg_prewarm` the index pages if the extension is allowed (commented in `tuning.sql`). `written=` in a plan means hint bits were being set because the table had not been vacuumed.

## Search architecture (design; the app implements the hybrid path)

**Keyword / BM25 / Postgres FTS / trigram:** names, ICD-10, LOINC, IDs, facilities, exact phrases.

**Semantic:** vectors from `embedding` text on encounters, order_details, diagnoses.

**Filters (do not embed):** dates, facilities, `result_flag`, `order_status`, `dx_family`, `patient_id`, insurance, `is_high_utilizer`.

**Hybrid:** filter first, retrieve keyword + vector candidates, fuse scores, return patient-joined hits.

Possible serving grains for Lakebase (vectors already exist on every row in the lakehouse):

1. Diagnosis documents (best clinical narrative).
2. Lab-result documents (delay / outreach story).
3. Encounter complaints (optional).

Do **not** default to syncing every `order_details` row (20M) to Lakebase. Prefer a subset: delayed Frederick labs, abnormal/critical flags, recent visits, or a sampled gold set plus the incident cohort.

## Coding conventions in this repo

- Databricks SOURCE notebooks: `# Databricks notebook source`, cells split by `# COMMAND ----------`, markdown via `# MAGIC %md`.
- Fully qualify `crisp.bronze.table`; do not rely on `USE CATALOG`.
- Deterministic hashes + `F.rand(integer_seed)` — **integer seeds only**, never a Column.
- A `F.rand`/`F.randn` draw referenced more than once (multiple `.when` branches, or reused across columns) must be materialized with `.withColumn("_x_r", F.rand(n))` and read via `F.col`. Inline reuse re-evaluates per reference and short-circuited `CASE` branches drift (verified on serverless: 50/25/25 became 50/37.5/12.5).
- Timestamps: use `F.timestamp_seconds(...)`, not `F.from_unixtime` (returns STRING).
- `pick_from` is 1-based `element_at` on a Python list via `F.lit(values)`.
- Overwrite Delta with `.option("overwriteSchema", "true")`.
- After write: CDF `delta.enableChangeDataFeed = true`, then `CLUSTER BY` patient-oriented keys.
